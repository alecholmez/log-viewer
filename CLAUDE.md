# Log Viewer

A virtual dyno: reads ECU logs (Haltech NSP `PCLog_*.csv` today), estimates wheel power, and reports what to change in the tune.
One codebase for macOS, Windows, iPhone and iPad: Rust core, TypeScript canvas UI (no framework), Tauri 2 shell.
See README.md for layout, commands and log import paths.

## Commands

- `npm install` then `npm run app` — desktop app in dev mode (`tauri dev`). `./run-app.command` does the same and logs to `run-app.log`.
- `npm run app:build` — installers for the current OS.
- The Mac app is installed once, in `/Applications`. After `npm run app:build`, move the new bundle there in place of the old one (`ditto`, then delete the bundle under `src-tauri/target`) and open it from there, so the Mac has one Log Viewer.
- `npm run test:core` — core against `crates/core/tests/golden.json` (snapshot from `testdata/logs`) plus library, switch, chip, log list and smoothing tests.
- `npm run build && cargo build --release -p logviewer-dev && npm run test:ui` — Playwright end-to-end test of the UI against the real core over HTTP.
- `npm run core -- --dir .logviewer` + `npm run dev` — UI in a browser without the native shell.
- `npm run site:shots` — retakes the website's screenshots in `site/img` from the real UI (same builds as the UI test). Preview the site with `python3 -m http.server 4173 -d site`.
- After an intended analysis change: `UPDATE_GOLDEN=1 cargo test -p logviewer-core`.
  The snapshot was made on Linux x86-64. Refreshing it on another CPU also rewrites the last digit of thousands of numbers, all inside the test's 1e-6 tolerance. For a small change, add the new values to the existing file instead.

## Rules for this project

- All numbers are computed in `crates/core`. The UI formats and draws; it does not analyse.
- Every platform goes through `Session::dispatch` (`crates/core/src/session.rs`). Add a command there, then expose it in `src/api.ts`.
- `!(x > y)` comparisons in the core are deliberate: they are also true for NaN (a missing sample).
- Smoothing changes only what is drawn: the power curve, its peaks and the weight band. Findings and the fuel check read the curve as computed, so a display setting never changes the diagnosis.
- UI copy: minimal and direct. No metaphors or analogies. Call things what they are ("Ignition table", "Fuel table", "Accelerator pedal", "Throttle plate").
- Findings are the product. Each one states evidence from the log, why it matters, and numbered changes with values derived from the data. Readers range from tuners to people starting from a base map.
- NSP unit scaling in `haltech.rs` was inferred from logs, not from Haltech documentation.
- Other ECUs (Link next) go in a module beside `haltech.rs`; the dyno and tables use only the channel roles in `log.rs`.
- Switches and states: what is a switch (samples of 0 and 1, and a declared `DisplayMaxMin` within 0 to 2), which channels are one signal (grouped once per log: same start, same changes each at most one sample apart, missing at the same samples) and a switch chip's spans are decided in `crates/core/src/switches.rs`; what is a state (not a switch, `Type` Raw or Gear, whole numbers, two to eight values, a declared range no wider than 128 where a NaN bound fails, no more than two changes a second over the log, not a `Data Log ` channel) and its sections in `crates/core/src/states.rs`, with the NSP parts (`has_no_unit`, `is_logger_channel`) in `haltech.rs`; the span, the order and the rule for the limits (keeping those that change least) in `crates/core/src/span.rs`, with the limits themselves as `MAX_SWITCHES` (twelve) in `switches.rs` and `MAX_STATES` (eight) in `states.rs`. A switch chip is built from the group's shortest name alone. `src/chips.ts` and `src/charts.ts` read and draw what the core returns and read no samples for it. Their values are tested in `crates/core/tests/switches.rs` and `crates/core/tests/chips.rs`, not in the golden snapshot. The chips and the traces are drawn together by `drawReplay` in `src/app.ts`, never the traces alone. `chipsWanted` in `src/state.ts` is the one rule for when chips are asked for and their room is kept.
- `serde_json` keeps its `float_roundtrip` feature (`crates/core/Cargo.toml`). The UI sends a span's ends as text and compares them, to the bit, with the ends in the core's answer; without the feature about one time in eleven is read back a hair off and a switch that is on at the end of the span reads Off there. Pinned in `crates/core/tests/chips.rs` and in the UI test.
- The log list's facts are the core's: a log's start (`startedAt` in `logs`, read in `haltech.rs` from the date in the `Log :` header line and the first row's 24-hour clock), the library's order (`refresh` in `session.rs`: by start, then by file name, logs with no start last), and the sentence that says what a pull is and why a log has none (`pull_rule` and `why_no_pull` in `dyno.rs`, written from the constants `detect_pulls` uses; `overview` carries them as `pullRule` and `noPulls`). A stretch's length is compared with `MIN_DUR` in whole milliseconds (`millis` in `dyno.rs`), never as the difference of two row times, which can come out a hair under the true length: a stretch of exactly 1.2 s is a pull, and a reason never writes its length as less. A stretch that gained no RPM is never the one a reason names. `README.md` states the same numbers by hand: change them there when a constant changes. The UI writes `startedAt` as `Apr 17, 1:45 pm` from its text (`startLabel` in `src/state.ts`), never through `Date`, so the machine's zone cannot move it. They are tested in `crates/core/tests/log_list.rs`, not in the golden snapshot.
- `renderLogs` rebuilds the list from scratch. Every control in it carries a `data-fid`, and the control that had focus gets it back in the new list, without scrolling it. Which logs with no pull are open is `openLogs` in `src/app.ts`, and is not saved.
- In a window 860px wide or less the log list scrolls in its own box (`.logs` in `src/styles.css`). The box is padded on every side so that the focus ring of a control at its edge is not cut off (12px at the top, bottom and left, 14px at the right), and each of its margins takes 12px of that room back, so the rows sit where they would without the padding, except on the right, where they end 2px short of it. A control added to the list must still show its whole ring there: the UI test measures every control in the list at phone width.
- Messages to the person go through `src/messages.ts`: `say` for a result, `progress` for work under way, `fail` for a failure. Nothing else writes to `#status`.
- Colours: no raw colour in a rule outside the token blocks of `src/styles.css`. Text on a colour uses the `--on-…` tokens; text is at least 4.5:1 and a line or mark at least 3:1.
